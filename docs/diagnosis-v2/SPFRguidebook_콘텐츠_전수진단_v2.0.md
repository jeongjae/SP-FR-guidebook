## 0. 네 줄 요약

1. **엔트리 315개를 전수 판정했다.** 관광지·도보코스 191, 식당·시장·카페 124. 상용 가이드북의 필수 정보항목 충족률은 **49.1%** — 절반이 비어 있다.

2. **비어 있는 곳이 일정하다.** 소개·의미(75%)·소요시간(69%)·관람요령(62%)은 상용 수준을 넘는데, **휴관일 37% · 예약 32% · 사진 45%**, 식당은 **찾아가는 법 13% · 휴무일 15%**다. 즉 "읽을거리는 훌륭하고 실행정보는 없다."

3. **정확도 오류 61건(그중 high 22건)이 살아 있다. 그리고 그 절반(31건)은 어제 이미 확정값을 찾아낸 항목이다.** Palais des Papes €17(→€19.50), Pont du Gard "야외 €8"(→무료), Nice 교통 €1.80(→€1.70), 렌터카 9/20 반납(→9/19 조기반납) — 8/16 진단이 잡아낸 것들이 원고에 그대로 남았다.

4. **따라서 이 진단의 결론은 "무엇을 더 조사해야 하나"가 아니다. "조사한 것이 원고에 들어가는 경로가 없다"이다.** 이 구조를 고치지 않으면 다음 진단도 같은 61건을 다시 발견한다. §5와 §7이 그 해법이다.

## 1. 조사 방법 — 중복 조사를 어떻게 막았나

이번 진단은 "다시 전부 조사한다"를 하지 않았다. 그 자체가 이 프로젝트의 낭비 구조이기 때문이다.

| 단계 | 방법 |
|---|---|
| ① **확정 사실 원장 구축** | 8/16 진단·핸드오프 §6·Jason 확정 결정 7건을 **`fact_ledger.md` 1개 파일**로 통합. 요금·시간·휴관·교통 확정값 약 90건 |
| ② **원장 우선 대조** | 8개 지역 병렬 에이전트에게 **"원장에 있는 값은 절대 웹 재검증 금지"**를 강제. 원고 값과 원장 값을 대조만 함 |
| ③ **선별 신규 검증** | 원장에 없고(`?`) + 확정 일정에 영향 주는 항목만 공식 소스 조회. **총 75건 시행** (성공 67 · 접근실패 8) |
| ④ **자동 판정** | 정보항목 충족은 에이전트 판정 후 스크립트로 집계 — 눈대중 금지 |
| ⑤ **요일 정합 자동 대조** | `itinerary.json`에서 Day↔날짜↔요일↔지역 표를 생성해 전 지역 공통 기준으로 사용 (CSV의 Day 밀림 버그 회피) |

**효과:** 어제 세션이 약 288건을 조사한 데 비해, 이번은 **신규 웹 조회 75건**으로 같은 범위를 덮었다. 중복 조사 74% 절감.

**한계:** 원장 자체가 8/16 기준이므로, 원장 값이 그 사이 바뀌었다면 잡지 못한다. 하루 차이이므로 실질 위험은 낮다.

## 5. ★ 핵심 발견 — 문제는 조사가 아니라 반영 경로다

### 5-1. 숫자가 말하는 것

**X 오류 61건 중 31건(51%)은 8/16 진단이 이미 정답을 찾아낸 항목이다.**

하루 사이에 PR #146이 병합되며 8개 챕터가 재편됐다. 그 재편은 "원문 충실도 보존"을 원칙으로 삼았고 — 원칙 자체는 옳았지만 — 그 결과 **틀린 원문이 새 구조 안에 그대로 이식됐다.** 어제 확정한 €19.50은 어디에도 들어가지 않았다.

### 5-2. 왜 이런 일이 반복되는가 — 세 가지 구조적 원인

**① 사실값의 단일 소스가 없다.**
같은 요금이 본문·실행표·예약카드·경비표·확인목록에 각각 하드코딩돼 있다. Navigo 요금이 파리 챕터 안에서만 3개 값으로 존재한다. 한 곳을 고쳐도 나머지가 남고, 빌드는 아무것도 잡지 못한다.

**② 검증 결과와 원고를 잇는 것이 사람의 기억뿐이다.**
검증은 진단서(Markdown)에 쌓이고, 원고는 별도 파일에 있다. 둘을 잇는 것은 "지시서를 읽고 손으로 고친다"뿐이다. 지시서가 지목한 위치(`§11`, `예약카드`)는 PR #146의 구조 개편으로 이미 사라졌다.

**③ `{{badge:pending}}`가 "확인 완료" 표시로 오용된다.**
282건의 pending 배지 중 상당수가 "복수 출처 확인 완료 · 출발 전 재확인"으로 쓰여 있다. Nice 교통요금이 정확히 그랬다 — **"복수 출처 확인"이라고 적힌 값이 전 항목 오류였고, 그 표시 때문에 아무도 다시 보지 않았다.**

### 5-3. 그래서 v1.1 진단의 P2("나중에")를 P0로 올려야 한다

v1.1은 "동일 사실 다중 하드코딩 제거"를 P2(여행 후)로 뒀다. 이번 진단은 이것을 **P0로 재분류한다.** 이 구조를 안 고치면 남은 12일 동안 61건을 손으로 고쳐도, 다음 구조 변경에서 다시 사라진다.

## 7. 개선 방법론 — 중복 조사·중복 축적을 막는 설계

이 절이 이번 요청의 핵심이다. **"어떻게 조사할까"가 아니라 "조사한 것이 두 번 다시 사라지지 않게 하는 구조"** 를 정의한다.

### 7-1. 단일 사실 소스 — `data/place-facts.json`

모든 요금·운영시간·휴관일·예약조건·교통값을 **placeId 기준 1곳**에만 둔다.

```json
{
  "palais-des-papes": {
    "displayName": "Palais des Papes",
    "address": "Place du Palais, 84000 Avignon",
    "facts": {
      "hours":   {"value":"3/1–11/1 09:00–19:00","source":"https://palais-des-papes.com/...","verified_at":"2026-08-16","confidence":"official","ttl_days":90},
      "price_adult": {"value":"€16","note":"통합권(궁+정원+다리) €19.50","source":"...","verified_at":"2026-08-16","confidence":"official","ttl_days":180},
      "closed":  {"value":"연중무휴","source":"...","verified_at":"2026-08-16","confidence":"official","ttl_days":180},
      "booking": {"value":"의무 아님(권장)","source":"...","verified_at":"2026-08-16","confidence":"official","ttl_days":180}
    }
  }
}
```

**원고는 값을 쓰지 않고 토큰으로 참조한다.**

```markdown
- **요금**: {{fact:palais-des-papes.price_adult}}
- **운영**: {{fact:palais-des-papes.hours}} · {{fact:palais-des-papes.closed}}
```

빌드가 주입하므로 **한 곳을 고치면 본문·실행표·예약카드·경비표가 동시에 바뀐다.** §5-2①이 구조적으로 불가능해진다.

### 7-2. 조사 큐 — `data/verify-queue.csv`

**조사 착수 전에 반드시 이 큐를 생성한다. 큐에 없는 것은 조사하지 않는다.**

| 열 | 의미 |
|---|---|
| `placeId` / `fact_key` | 대상 |
| `status` | `MISSING`(값 없음) / `STALE`(TTL 초과) / `CONFLICT`(문서 내 2값) / `FRESH`(조사 불필요) |
| `priority` | P0(확정 일정 영향) / P1 / P2 |
| `last_attempt` / `blocked_reason` | 접근 실패 기록 — **같은 도메인을 다음 세션이 또 두드리지 않게 한다** |

생성 규칙: `place-facts.json`에 있고 TTL 이내면 **`FRESH` → 조사 대상에서 자동 제외.** 이번 세션이 수동으로 한 일(원장 대조)을 스크립트가 하게 만드는 것이다.

**TTL 정책**

| 사실 유형 | TTL | 근거 |
|---|---:|---|
| 요금 | 180일 | 연 1–2회 개정 |
| 정규 운영시간·휴관일 | 90일 | 계절제 전환 |
| 특별전 회기·이벤트 | 30일 | 변동 잦음 |
| 교통 시각표·운임 | 30일 | 개편·파업 |
| 식당 영업일 | 60일 | 휴가·폐업 |
| **여행 D-7 이후** | 전 항목 재확인 대상 | 출발 직전 게이트 |

### 7-3. 가드 6종 — 빌드가 잡게 한다

| **G6 신선도** | `verified_at` + TTL 초과 사실이 원고에 노출되면 배지 자동 강등 | 경고 |

### 7-4. 배지 의미 3분할

현행 `{{badge:pending}}` 단일 표기가 §5-2③의 사고를 낳았다. 다음으로 나눈다.

| 배지 | 의미 | 표시 |
|---|---|---|
| `{{fact:...}}` | 확인된 값 (소스·확인일 보유) | 값 + 확인일 |
| `{{badge:unverified}}` | **아직 조사 안 함** | "미확인 — 현장 확인 필요" |
| `{{badge:unreachable}}` | 공식 소스 접근 실패 | "공식 확인 불가 — 전화 확인" + 전화번호 |
| `{{badge:field-recheck}}` | 확인 완료, 변동 가능 | 값 + "출발 전 재확인" |

### 7-5. 작업 순서 원칙

```
① 사실 인프라 (place-facts.json + 가드)   ← 먼저. 그릇을 만든다
② P0 오류 21건을 인프라 위에서 수정        ← 고친 것이 사라지지 않는다
③ 조사 큐 생성 → 미검증만 조사 → DB 적재   ← 중복 조사 0
④ 정보항목 공란 채움 (큐 소진)
⑤ D-7 최종 게이트
```

**②를 ①보다 먼저 하면 이번 진단이 무의미해진다.** 8/16의 교훈이 그것이다.

## 8. 자체 한계 고지

- 정보항목 판정은 지역별 에이전트의 판정을 스크립트로 집계한 것이다. 판정 기준은 통일했으나 경계 사례(P 판정)의 지역 간 편차가 있을 수 있다. **개별 장소 판정은 원고 확인이 필요하며, 지역 간 비교는 경향 판단용이다.**
- 사실 대조는 **8/16 확정 원장 + 이번 신규 검증 75건** 기준이다. 원장에 없고 이번에 조사하지 않은 133건은 "오류 없음"이 아니라 **"모른다"** 이다.
- 공식 소스 접근 실패 8건은 우회 시도를 하지 않았다. 오류가 아니라는 뜻이 아니다.
- 전화·현장 확인이 필요한 항목(식당 영업일, 렌터카 지점 운영시간, Hertz 조기반납 승인)은 여전히 미확정이며 **Claude가 처리할 수 없다.**
- 등급 정규화는 문자열 패턴 매칭이다. 80종 표기 중 일부는 오분류 가능성이 있다.
