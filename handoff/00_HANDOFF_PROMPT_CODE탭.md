# Claude 앱 Code 탭 — 인계 절차와 프롬프트

Code 탭은 클라우드에서 **GitHub 저장소를 상대로** 동작한다. 로컬 파일시스템이 없으므로 인계 자료가 저장소 안에 있어야 한다.

---

## 1. 준비 — 폰에서 5분

파일 53개를 따로 올릴 필요 없다. **zip 하나만 올리고 Claude Code에게 풀게 한다.**

1. `SP-FR-guidebook_handoff_20260801.zip` 을 폰에 다운로드
2. 모바일 브라우저에서 `github.com/jeongjae/SP-FR-guidebook` 접속
3. **Add file → Upload files**
4. zip 선택 → **저장소 루트**에 업로드
5. 커밋 메시지 `chore: 개선 인계 자료 zip 추가` → **main 브랜치에 직접 커밋**

> **main에 직접 커밋해도 안전한가** — `.github/workflows/pages.yml`이 main 푸시마다 빌드·배포한다.
> zip은 `source/`·`build/` 밖의 루트 파일이라 빌드 산출물에 영향을 주지 않는다.
> 다만 워크플로가 한 번 도는 것은 정상이다.

## 2. 첫 프롬프트

Code 탭에서 이 저장소로 새 세션을 열고 아래를 그대로 붙여넣는다.

```
2026년 유럽 43일 여행 가이드북 웹사이트를 개선한다.
출발일이 8월 29일이라 D-28이다. 여행 중에 실제로 쓸 도구다.

## 0. 인계 자료 압축 해제

저장소 루트에 SP-FR-guidebook_handoff_20260801.zip 이 있다. 먼저 이것부터 처리해라.

  unzip -o SP-FR-guidebook_handoff_20260801.zip
  rm SP-FR-guidebook_handoff_20260801.zip
  ls -R handoff | head -60

handoff/ 를 저장소에 남긴다. 이후 세션에서도 계속 참조한다.
.gitignore 에 넣지 마라.

풀고 나면 이 순서로 읽어라.
  1. handoff/README.md
  2. handoff/01_plan/08_사이트_종합개선_실행계획서_v1.0.md   ← 주 문서
  3. handoff/01_plan/10_명명규칙_v1.0.md

## 1. 저장소 구조 — 반드시 이해하고 시작해라

이 저장소는 생성 파이프라인을 갖고 있다.

  source/            원본 (MD 11챕터, 지도, xlsx)
  build/build.py     빌드 스크립트 (1175행)
  build/assets/      style.css, nav.js 원본
  site/              ← 빌드 산출물. 직접 편집 금지
  .github/workflows/pages.yml   main 푸시 → 자동 빌드 → gh-pages 배포

빌드: pip install markdown openpyxl && python3 build/build.py

## 2. 절대 규칙

1. site/ 를 직접 편집하지 마라. 다음 빌드에 덮어써진다.
   본문은 source/, 구조·템플릿은 build/build.py, CSS·JS는 build/assets/ 에서 고친다.
2. 런타임 서드파티 의존성을 추가하지 마라. 현재 0개고 완전 오프라인으로 동작해야 한다.
3. 미확정값을 확정처럼 표시하지 마라. 예약이 아직 안 잠겼다.
   숙소 후보 주소를 확정으로 믿고 이동하는 것이 이 프로젝트 최악의 사고다.
4. 검증 안 된 사실을 쓰지 마라. 현장에서 틀린 정보는 없느니만 못하다.
5. 이름을 번호로 짓지 마라. 지명으로 짓는다. handoff/01_plan/10_명명규칙_v1.0.md 참조.
6. main 에 직접 푸시하지 마라. 브랜치를 파고 PR 을 올려라.
   main 푸시는 즉시 배포로 이어진다.

## 3. 지금 할 일 — T0 정찰

작업을 시작하기 전에 상태부터 확인한다.

1. python3 build/build.py 를 실행해 빌드가 통과하는지 확인
2. site/ 를 /tmp/site_before 로 스냅샷
3. 계획서 2장의 실측값을 재측정해 대조표를 만든다. 특히:
   - VISUAL 토큰 노출 수            기대 68
     grep -ro "{{VISUAL:" site/chapters/ | wc -l
   - 04·07 챕터 Day 헤딩 레벨       H3 사용 여부
     grep -cE "^<h3[^>]*>Day [0-9]" site/chapters/04.html site/chapters/07.html
   - source/ 실제 구조가 README 및 build.py 상수와 일치하는지
4. 불일치가 있으면 작업을 진행하지 말고 보고해라.

정찰 결과를 보고하고 멈춰라. 코드는 아직 고치지 마라.
```

## 5. Code 탭의 한계 — 알고 시작할 것

| 한계 | 대응 |
|---|---|
| `./serve.sh` 로컬 확인 불가 | PR 머지 후 gh-pages 배포본을 폰으로 확인 |
| 시각 검증이 어렵다 | T3 CSS 교체 후 반드시 실기기로 확인. `handoff/02_assets/style_preview.html` 을 폰에서 먼저 열어 봐도 된다 |
| 긴 diff 리뷰가 폰에서 힘들다 | 마일스톤을 잘게 나눴다. 한 PR 을 크게 만들지 마라 |
| main 푸시 = 즉시 배포 | 반드시 브랜치 + PR. 빌드 통과 확인 후 머지 |

**모바일이 오히려 나은 작업도 있다.** KML 임포트 검증(T9)과 야외 주광 실측(T3 검수)은 폰이 필요하다.
