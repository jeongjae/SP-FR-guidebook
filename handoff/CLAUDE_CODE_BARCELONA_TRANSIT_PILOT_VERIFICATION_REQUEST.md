# Claude Code 독립 검증 요청 — Barcelona 숙박·생활·공공교통 파일럿

## 1. 목적

Barcelona 지역 페이지에 추가한 숙박·생활 실행 요약과 도시 공공교통 파일럿을 독립적으로 검증한다. 기존 원고의 분량 복원 여부가 아니라, 일정·daily card·공식 교통 출처와 교차 확인한 뒤 중복·편집 언어를 제거한 결과가 짧고 실행 가능한지를 판정한다.

검증자는 구현자의 판단을 전제로 삼지 말고, 사실·일정 연결·표현 밀도·회귀를 각각 반박 관점에서 확인한다.

## 2. 검증 대상

- 브랜치: `codex/stay-transport-guards`
- 기준 커밋: 이 문서가 포함된 최신 커밋
- 핵심 파일
  - `data/region-essentials.json`
  - `data/region-essentials.schema.json`
  - `data/transit-facts.json`
  - `data/transit-facts.schema.json`
  - `build/model.py`
  - `build/render.py`
  - `tests/test_stay_transport_guards.py`

이전 단계의 P0 사실 수정과 교차 지역 혼입 방지 커밋도 회귀 기준으로 포함한다.

## 3. 의도한 편집 원칙

1. 기존 장문 원고를 그대로 되살리지 않는다.
2. 일정과 직접 연결되지 않거나 다른 화면에서 충분히 제공되는 정보는 반복하지 않는다.
3. 지역 페이지에는 도착·출발·생활 필수·늦은 귀가·교통권 판단처럼 현장에서 결정을 바꾸는 정보만 둔다.
4. 교통권은 일반적인 관광 추천이 아니라 실제 Day 1~4 이동 횟수와 예외를 기준으로 추천한다.
5. 가격·이용 조건은 공식 운영기관 출처와 확인일·재확인일을 함께 보관한다.
6. 지역 페이지에서 관련 daily card로 직접 이동할 수 있어야 한다.

## 4. 구현 요약

- 지역별 실행 요약과 교통 사실을 원고에서 분리된 구조화 JSON으로 추가했다.
- JSON Schema가 필수 필드, 길이, 타입, 허용하지 않는 추가 필드를 검사한다.
- Barcelona 일정에 맞춰 다음 결론을 표시한다.
  - Day 2의 선택적 1회 승차 외에는 도보 중심이므로 사전 패스 구매를 권하지 않는다.
  - 실제 승차 때 단일권을 사용한다.
  - 두 사람 합계 승차가 4회 이상으로 늘 때만 공동 T-familiar를 검토한다.
  - T-casual은 현재 일정에 과다하다.
- 공항 Metro L9, Aerobús, Rodalies/Sitges를 시내 교통권과 혼동하지 않도록 예외로 분리했다.
- Day 1~4 적용 이동을 daily card 링크로 연결했다.

## 5. 독립 사실 검증 항목

공식 페이지를 새로 열어 다음을 재확인한다. 저장된 문구를 그대로 신뢰하지 않는다.

1. 2026년 TMB 단일권 €2.90
2. T-familiar 1 zone €11.50, 공동 사용, 8회
3. T-casual 1 zone €13.00, 1인용 10회
4. T-casual·T-familiar의 Airport T1/T2 Metro L9 Sud 사용 불가
5. 1존 통합권의 75분 및 최대 3회 환승 조건
6. TMB 버스와 일부 Metro 개찰구의 은행카드 단일권 구매·검증 방식
7. Rodalies 표의 승차 전 구매·검증 및 하차 때까지 보관 조건
8. 두 사람 합계 4회부터 €11.50 T-familiar가 단일권 4회 €11.60보다 낮다는 계산

데이터에 기록된 공식 URL을 우선 사용하고, 페이지가 변경되었으면 최신 공식 URL과 차이를 보고한다.

## 6. 일정 교차 검증 항목

`data/daily-cards/day-01.json`부터 `day-04.json`, 일정 정본, Barcelona 지역 장을 대조한다.

- Day 1: BCN T1 도착 후 숙소 이동
- Day 2: Sagrada Família→Gràcia만 대중교통 선택 가능
- Day 3: 도보 중심
- Day 4: Sants 이후 예약 렌터카 이동이 기본
- 지역 페이지의 Day 링크가 정확한 daily card로 이동하는지 확인
- 이동일 데이터가 다른 지역 교통 목록에 섞이지 않는지 확인

## 7. 콘텐츠 품질 판정

다음 질문에 각각 `PASS`, `PASS WITH NOTES`, `FAIL`로 답한다.

1. 숙박·생활 요약이 원고의 반복이나 여행 에세이 문구 없이 현장 행동을 바꾸는가?
2. 특정 약국·상점처럼 쉽게 낡는 정보를 억지로 고정하지 않으면서도 충분히 실행 가능한가?
3. 교통권 추천이 실제 일정과 두 사람 사용 조건에 맞는가?
4. 공항·시내·근교 교통의 요금 체계를 오해하게 만들 표현이 없는가?
5. 모바일 화면에서도 핵심 결론→상품 비교→이용법→예외→Day 링크 순서가 이해되는가?
6. 정보가 일정·지도·daily card와 중복되기보다 서로 연결되는가?
7. 이 구조를 Nice 등 다른 도시로 확장해도 출처와 일정 귀속을 검증할 수 있는가?

## 8. 실행 검증

```powershell
python -m unittest tests.test_stay_transport_guards -v
$env:SPFR_SITE_DIR = Join-Path $PWD '.claude-verify-site'
python build/site.py
```

생성된 `guide/barcelona.html`을 데스크톱과 모바일 폭에서 열어 다음을 확인한다.

- `도시 공공교통` 섹션 표시
- 상품 카드 3개와 공항 L9 불가 표기
- 공식 출처 접기 영역
- Day 1~4 링크
- 콘솔 오류 없음
- 교통 섹션이 기존 숙박·장소·일정 섹션을 가리지 않음

주의: 기존 `build/test_validation.py`는 작업 파일을 직접 바꾸는 fixture 문제가 알려져 있으므로 이번 독립 검증에서는 실행하지 말고, 필요하면 별도 복제본에서만 실행한다.

## 9. 범위 제외

- Hertz 관련 기존 사실·예약 쟁점은 사용자가 별도로 확인할 예정이므로 이번 판정의 차단 사유로 다루지 않는다.
- 이번 단계는 Barcelona 파일럿 검증이다. Nice 등 전 도시 확장은 파일럿 승인 후 진행한다.
- 기존 저장소의 G2/content audit 기저 실패는 이번 변경에서 새로 발생했는지 구분해서 보고한다.

## 10. 산출물 형식

`handoff/CLAUDE_CODE_BARCELONA_TRANSIT_PILOT_VERIFICATION_RESULT.md`에 다음 순서로 작성한다.

1. 최종 판정: `PASS`, `PASS WITH NOTES`, `FAIL`
2. 차단 이슈(있을 때만)
3. 사실 검증 표: 주장 / 공식 근거 / 판정 / 수정 제안
4. 일정·daily card 연결 검증
5. 중복 제거와 실행성 평가
6. 데스크톱·모바일 화면 검증
7. 회귀 테스트 결과
8. Barcelona 승인 후 Nice 확장 때 반드시 바꿔야 할 점

가능하면 검증 단계에서는 코드를 수정하지 말고 결과만 기록한다. 치명적 오류를 발견해 수정이 불가피하면, 결과 문서와 수정 커밋을 분리하고 변경 이유를 명시한다.
